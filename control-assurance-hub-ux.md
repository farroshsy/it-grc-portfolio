# Control Assurance Hub — Offline Product Blueprint

## Business Process Solved

The workspace answers a practical operating problem: **How does a control exception become owned engineering work and a defensible GRC closure decision?** It provides one place to intake evidence, test controls, record exceptions, decide treatment, track remediation, and communicate residual exposure. No external system is required for this workflow to function.

## Roles and Daily Jobs

| Role | Daily job in the workspace | Primary actions |
|---|---|---|
| Control owner | Prove that a control operated | Submit evidence, explain scope, respond to review notes |
| GRC analyst | Test evidence and make a control decision | Review evidence, record test result, create a finding, request retest |
| Engineering remediation owner | Resolve the technical gap | Review remediation acceptance criteria, update delivery state, provide closure evidence |
| Risk approver | Decide whether residual exposure can be tolerated | Approve or reject a time-bound risk acceptance |
| Management | See posture and unblock decisions | Review exceptions, aging remediation, and approval queue |

## Workspace Navigation

| Workspace area | User outcome | Core interaction |
|---|---|---|
| Command Center | Understand current posture and next decisions | View workflow KPIs and priority queue |
| Evidence Intake | Move owner evidence into review | Submit evidence against a control and move it to review |
| Control Tests | Turn evidence into a defensible conclusion | Record effective or exception test outcome |
| Findings & Remediation | Convert exceptions into owned treatment | Choose remediation or risk acceptance; assign owner and due date |
| PBC & Workpapers | Organize request-to-proof audit evidence | Inspect PBC status and sample-based test workpaper |
| Policy Pack | Reference expected operating behavior | Review access, change, incident, and vulnerability procedures |
| Connection Boundary | Prepare future engineering-ticket integration | See GitHub contract and offline status without requiring credentials |

## Offline-First Guardrail

All records in the initial scenario use the **Simulated Case Study** provenance label. The connection boundary will show `Not connected` or `Ready to create` until a user provides their own GitHub details later. It will never manufacture a live external ticket, certification, client result, or regulatory approval.
